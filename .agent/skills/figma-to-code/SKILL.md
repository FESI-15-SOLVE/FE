# Figma to TSX+Tailwind (Superpowers Engaged)

## Goal

Figma 선택 영역을 픽셀 단위로 동일하면서도, 프로젝트의 기존 컴포넌트/토큰/코드 컨벤션을 재사용하는 TSX 컴포넌트로 변환한다. Figma MCP가 주는 코드는 "시작점"이지 최종 코드가 아니다.

**이 스킬은 무조건 Presentational(순수 UI) 컴포넌트만 만든다.** 상태 및 에러 여부는 전부 `props`로 받아서 그대로 렌더링만 하며, 폼 검증 규칙·API 호출·라우팅 같은 비즈니스 로직은 철저히 배제한다. 이벤트는 콜백 props로 위임한다. 사용자가 "기능까지 다 구현해줘"라고 명시적으로 요청하더라도, 내부 로직을 짜지 말고 UI를 제어할 수 있는 고도화된 `props` 구조와 인터페이스만 설계한다.

**기본 UI 레이어는 shadcn/ui를 무조건 우선으로 한다.** 처음부터 원시 HTML 태그(`<button>`, `<input>` 등)로 스타일링하지 않고, `components/ui/`에 이미 설치된 shadcn 프리미티브가 있으면 그 위에서 확장한다. 없으면 새로 만들기 전에 사용자에게 shadcn CLI로 설치할지 반드시 물어보고 답변을 기다린다.

## When to use

- 사용자가 Figma 링크 또는 현재 선택 영역을 주고 컴포넌트/페이지 구현을 요청할 때
- figma-design-tokens 스킬이 이미 실행되어 프로젝트에 토큰이 세팅되어 있는 상태가 이상적

## Required flow (건너뛰지 말 것)

0. **[필수 코드베이스 조사 단계 - 건너뛰기 절대 금지]** 코드를 생성하기 전에 먼저 파일 탐색 툴(`list_dir` 등)을 사용하여 프로젝트의 `components/ui/` 폴더와 `tailwind.config.ts`(또는 `@theme` CSS), `globals.css`를 실제로 읽는다.
   - 탐색 결과 발견된 shadcn/ui 컴포넌트 목록을 마음속으로 lookup으로 만들어둔다. 이 조사 없이 바로 4단계(코드 생성)로 넘어가는 것은 금지된다.
   - 만약 `components/ui/` 폴더가 비어있거나 shadcn 컴포넌트가 없다면, **코드를 짜지 말고 즉시 중단한 뒤 "shadcn 컴포넌트가 발견되지 않았습니다. CLI로 설치할까요?"라고 사용자에게 물어본다.**
1. `get_design_context`로 정확한 노드의 구조화된 표현(기본 React+Tailwind)을 가져온다.
2. `get_screenshot`으로 해당 노드/variant의 시각적 레퍼런스를 받는다.
3. Code Connect 사용 가능 여부를 먼저 확인한다: `get_context_for_code_connect`를 호출해봐서 에러가 나면 아래 "Code Connect 없이 기존 컴포넌트 매칭" 절차로 대체한다. 에러 없이 매핑이 반환되면 그 매핑을 그대로 신뢰하고 기존 코드 컴포넌트를 재사용한다.
4. `get_design_context`가 반환한 모든 색상/spacing 수치를 0단계의 lookup 및 **Tailwind 정적 기본 스케일(Default Scale)**과 대조한다.
   - 피그마 픽셀 값을 무조건 대괄호(`-[48px]`)로 변환하지 말고, 테일윈드 기본 배수 스케일(예: `48px` -> `12`, `32px` -> `8`, `16px` -> `4`)로 **먼저 기계적인 스냅/수치 연산(px을 4로 나누기)**을 수행한다.
   - 프로젝트 정의 토큰 또는 기본 스케일과 ±2px 이내로 근접한 수치는 가장 가까운 정식 토큰 클래스로 자동 스냅하고 사유를 주석으로 명시한다.
5. **[superpowers 브레인스토밍 및 아키텍처 가이드]** 파일 위치와 네이밍, 컴포넌트의 추상화 단계를 짐작으로 결정하지 않는다.
   - 기존 구조가 애매하거나, 컴포넌트 합성(Compose) 패턴 기준이 모호한 경우 추측해서 코드를 짜지 말고 **즉시 중단 후 유저에게 질문**한다.
   - **[핵심]** 질문 시 단답형으로 묻지 않고, `superpowers` 브레인스토밍 모듈을 가동하여 **"프로젝트 도메인 맥락에 기반한 최적의 아키텍처/Props 설계 대안(Pros/Cons가 포함된 A안, B안)"을 최소 2개 이상 구체적으로 제시**하며 유저의 의사결정을 리드한다.
6. **디자인 증발 방지 및 최소 UI 보장:** 변환 후 placeholder 콘텐츠는 실제 데이터 모델에 맞게 props화하되, Figma의 오리지널 데이터가 껍데기만 남으면 안 된다. 개발자가 화면을 즉시 확인할 수 있도록 컴포넌트 내부 혹은 파일 하단에 **Figma에 있던 실제 텍스트와 데이터를 기본값(`defaultProps` 또는 프리뷰용 더미 데이터 객체)으로 바인딩하여 출력**한다.
7. 완성된 컴포넌트를 `get_screenshot` 결과와 비교해 레이아웃/spacing/color가 1:1로 맞는지 검증한다.
8. **[자가 검증 하네스 단계 - 셀프 체크리스트 검사]** 생성된 최종 코드가 아래 `# Self-Verification Harness Checklist` 항목을 모두 충족하는지 한 줄씩 검사한다. 통과하지 못한 항목이 있다면 코드를 즉시 수정하고, 최종 출력 시 체크리스트 결과를 보고서 형태로 첨부한다.

## Code Connect 없이 기존 컴포넌트 매칭 (Org/Enterprise 플랜이 아닐 때)

`Youtube`에서 반복적으로 등장하는 인스턴스 이름을 먼저 목록화하고, 프로젝트 코드베이스를 `grep`/`glob`으로 검색해서 이미 존재하는 컴포넌트가 있는지 확인한다. 존재한다면 원시 마크업으로 새로 만들지 않고 import해서 조합한다.

## 여러 상태(state) 및 브레이크포인트를 하나의 컴포넌트로 병합하기

- **상태 병합**: 상태별 독립 프레임들을 diff하여 `type State = 'default' | 'error' | 'complete'` 같은 단일 유니온 props로 모델링하고 **하나의** 컴포넌트로 병합한다. 내부 비즈니스 로직(예: `useState`, `useEffect`)은 절대 컴포넌트 내부에 작성하지 않는다.
- **반응형 병합**: 하나의 컴포넌트 안에서 `md:`, `lg:` 접두사로 반응형 클래스를 표현한다. 브레이크포인트마다 별도 컴포넌트 파일을 만들지 않는다.

## 컴포넌트 합성 원칙: 확장(compose) vs 오버로드

- **시각적 variant** (크기, 색상, disabled 여부 등): 기존 프리미티브의 `cva` variant/prop으로 추가한다.
- **도메인 개념** (OAuth provider, 특정 서비스 주문 상태 등): 새 컴포넌트로 분리해서 기존 프리미티브를 내부적으로 감싸 쓴다(Compose). 프리미티브는 항상 도메인을 몰라야 한다.

## Constraints

- **절대 금지 (Strictly Prohibited):** 컴포넌트 내부에 상태 관리 및 데이터 페칭 훅(`useState`, `useEffect`, `useQuery`, `useForm` 등)을 **단 하나도 작성하지 않는다.** 모든 인터랙션 결과는 상위에서 제어할 수 있도록 오직 `props` 구조로만 설계한다.
- **임의의 인터랙션 구현 금지 (No Guesswork Interaction):** Figma 프로토타입 스펙이나 명시적인 지침이 없는 한, `hover:scale-105`, `transition-all`, 임의의 키프레임 애니메이션 등을 **독단적으로 판단하여 구현하지 않는다.** 필요하다고 판단되는 인터랙션 효과는 코드가 아닌 **`superpowers` 브레인스토밍 제안 목록**에 텍스트 아이디어 형태로 분리하여 사용자에게 컨펌을 받는다.
- **임의의 대괄호 하드코딩 엄격 금지 (No Lazy Arbitrary Values):** `w-[48px]`, `h-[32px]`와 같이 테일윈드 기본 4의 배수 스케일(`w-12`, `h-8`)로 변환 가능한 픽셀 값은 **절대 arbitrary value(`-[`) 패턴으로 작성하지 않는다.** 피그마에 적힌 정수 px 값이 테일윈드 기본 스케일로 나뉘는 값인지 수학적으로 먼저 연산해야 하며, 프로젝트 전용 커스텀 토큰에도 없고 테일윈드 기본 스케일로도 표현 불가능한 극소수의 예외 케이스(예: 디자인상 필수적인 `top-[13px]` 등)에 한해서만 주석 기술 후 허용한다.

## Self-Verification Harness Checklist

코드를 최종 출력하기 전, AI는 반드시 아래 체크리스트를 스캔하고 통과 여부를 검증해야 한다.

1. [ ] **비즈니스 로직 Free**: 내부에 `useState`, `useEffect`, `useForm` 등 비즈니스 로직/훅이 100% 배제되었는가?
2. [ ] **shadcn/ui 우선 활용 및 합성**: 프로젝트의 `components/ui/` 폴더를 확인하고 기존 프리미티브를 상속/합성(Compose)했는가?
3. [ ] **디자인 무결성**: 피그마 디자인에 명시되어 있던 기본 텍스트나 placeholder 데이터가 지워지지 않고 프리뷰용 더미 객체 형태로 코드 내에 살아있는가?
4. [ ] **정적 가이드 준수 (임의 애니메이션 배제)**: 지침에 없거나 프로젝트 컨벤션이 확인되지 않은 임의의 호버 효과, 애니메이션 클래스가 코드에 하드코딩되지 않았는가?
5. [ ] **대괄호 하드코딩 제거 및 기본 스케일 준수**: 생성된 코드 내의 모든 `-[` 패턴을 정규식으로 전수 검사하여, `48px` -> `12` 처럼 테일윈드 내장 4의 배수 표준 크기나 커스텀 토큰으로 대체할 수 있는 항목을 전부 완벽하게 치환했는가?
6. [ ] **단일 컴포넌트 수렴**: 여러 상태/브레이크포인트 프레임을 하나의 컴포넌트 내부에서 반응형 접두사와 유니온 상태 타입으로 병합했는가?
7. [ ] **Superpowers 아키텍처 싱크**: 설계가 모호하거나 추가적인 UX 개선이 필요한 지점에서 유저에게 `superpowers` 기반의 구조적 대안(Pros/Cons)을 제시하고 조율을 거쳤는가?

## Output

- 완성된 `.tsx` 컴포넌트 파일 (Figma 원본 데이터 기반의 프리뷰 더미 데이터 객체가 매핑되어 있어야 함)
- **Harness 검증 결과 보고서**: 위의 `# Self-Verification Harness Checklist` 7개 항목에 대한 통과 여부(`[X]` 표시) 및 상세 사유 요약
- 어떤 기존 컴포넌트/토큰을 재사용했는지, 그리고 왜 이 폴더 위치를 골랐는지 요약
- 어떤 shadcn 프리미티브를 그대로 썼고, 어떤 걸 새로 감싸서(compose) 만들었는지 기록
- 발견된 arbitrary value 목록과 각각의 사유 (없으면 "arbitrary value 없음"이라고 명시)
